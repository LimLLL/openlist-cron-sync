用途：记录把计划动作与执行尝试分两层保存的取舍与后果。

范围：已接受的设计决策；字段与约束以执行数据表为准。

# ADR 0010：逻辑操作与执行尝试分层

- 状态：accepted
- 日期：2026-10-29
- 决策者：项目维护者

## 背景

v0.0.8 及更早版本把每次自动重试保存为一条新的 operations 行，用 retry_of 指向首次尝试、attempt_no 计数，并为新行分配新的 seq、复制和改接依赖。结果：

- 一个文件失败一次、重试成功后，操作列表出现一条失败和一条成功，看起来像两个动作。尝试列已经有次数，这两行是重复表达。
- “当前结果”要在统计、重试候选、执行器、历史清理等多处各自推导“同一根的最后一次尝试”，口径分散。
- 结束旧尝试与创建新尝试分两个事务，崩溃窗口里可能留下已失败但没有安排重试的动作。
- 历史清理要沿 retry_of 计算跨 Run 引用闭包。

生产库 658 MB，其中约 265 MB 是删除历史后留下的空闲页，另有 operations 的路径索引约 69 MB。

## 决策

- operations 一行是一个计划动作：身份、seq、计划字段与依赖在重试期间不变，status 与 ended_at 表示该动作的结果。替换的删旧与写新、残留清理仍各自是独立动作。
- operation_attempts 一行是一次执行尝试，保存远端任务、分片会话、字节、错误和时钟；第一次尝试的 ID 与动作相同，旧版本的尝试行原样成为尝试，旧 ID 仍可打开详情。
- 依赖只连接动作。结束一次尝试与是否安排下一次在同一事务提交。
- API 列表返回动作摘要（含 attemptCount），详情内嵌全部尝试。
- 升级迁移在一个事务内严格校验旧链并整体转换；旧版本留下的 REMOTE_TASK_CHANGED 维护行在确认没有剩余责任后删除。
- 新库从建库起使用 SQLite 增量自动回收；旧库在迁移提交后做一次 VACUUM 并切换该模式，之后每天历史清理结束时把空闲页归还给文件系统。同时去掉不再使用的路径与重试索引。

## 考虑的替代方案

- 列表按根分组只显示最后一次尝试：只改展示，统计和各处“最后一次尝试”推导仍然分散，重试的两个事务也还在。
- 给重试成功的旧失败行加“已重试”标记：等于新增一种状态，与“重试成功就是成功”的预期相反。
- 只做 VACUUM、不切换增量回收：一次能收回空间，但每次清理历史后文件又会停在峰值大小。

## 后果

- 收益：一个动作一行；统计、重试候选、执行和清理读同一份结果；重试安排不再有半提交窗口；历史清理按单个 Run 进行。迁移和压缩后，生产规模测试中数据库约从 648 MB 降到 366 MB。
- 代价：读取当前尝试需要连接两张表；API 删除操作顶层的 retryOf，attemptNo、task、multipart 移入详情的尝试记录，includeMaintenance 参数删除，属于不兼容变更。
- 已接受风险：迁移期间需要额外的 WAL 和临时文件空间；旧库首次启动多一次 VACUUM。空间不足时跳过压缩、照常启动，下次启动再试。降级必须恢复升级前备份。
- 不提供的保证：VACUUM 期间不保证可抵御并发磁盘占用；空间预检只是估算。
