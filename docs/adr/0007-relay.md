# ADR 0007：分片流水线 relay

- 状态：accepted
- 日期：2026-10-19
- 决策者：项目维护者

## 背景

relay 是默认创建方式，要支持任意实例关系和大文件。下载与上传速度常不一致；整文件流式 PUT 会让下载被上传拖住，失败时整文件重来，中止 PUT 后目标状态也难以判定。OpenList 自 v4.2.5 起提供分片上传接口（init/chunk/complete/status/abort）：分片幂等、可并发乱序、可单独重传，complete 等待驱动结果。

## 决策

- 下载 worker 与上传 worker 解耦，中间是本地磁盘 spool（固定 1 MiB 块）。下载写完一个块就去处理下一个块或文件，不等上传。
- 上传使用 OpenList 分片接口，chunk 由连续块拼成，大小取 init 返回值；确认后释放块。0 字节文件走普通 put。
- spool 默认可用全部剩余空间，只为 SQLite 保留固定余量；空间不足时下载暂停，真实写盘失败才报错。
- 每个 (文件, Target) 各自下载；不做跨目标共享，也不做跨本服务重启的续传。
- 最低支持 OpenList 4.2.5。

## 考虑的替代方案

- 整文件流式 PUT：下载被上传拖住，失败整文件重来，中止后的目标状态难判定。
- 整文件落盘再上传：大文件需要等量磁盘。
- 多目标共享下载：需要分组准入和引用计数，最慢目标拖住整组；进入 backlog。

## 后果

- 收益：下载与上传并行；chunk 级重传不需重新下载；最后一个 chunk 等源 EOF 后才发出，源异常不会提交截断文件；大文件不需等量磁盘。
- 代价：需要本地磁盘和更多协调逻辑；同实例同 storage 也要完整下载再上传；多目标时源被下载多次。
- 已接受风险：init 一执行就启动驱动写入；abort 和 session 过期都不证明远端已停止。主动 abort 记 failed，接受迟到清理的风险；取消、关机和响应丢失记 unknown 并隔离。
